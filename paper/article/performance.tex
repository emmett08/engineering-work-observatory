\section{Computing repeated cohort summaries}
\label{sec:performance}

For a fixed set of tasks and assessment delay $\Delta$, each acceptance deadline $\tau$ determines two sums. One counts the output scores for tasks accepted by the deadline, and the other counts labour through task age $\tau+\Delta$. How can we recalculate these sums for many deadlines efficiently? Sort acceptance ages and labour interval end ages once, storing cumulative output scores and cumulative person-hours alongside them. Each later deadline then requires only two binary searches. A full scan calculates the same totals by checking every age and weight again. The comparison below measures the execution time of these two methods. Establishing an effect of AI assistance on human labour requires a separate causal study.

\subsection{The fields in an output or labour record}

Each input record has two numeric fields, \texttt{age} and \texttt{weight}. The output list $A=((a_i,w_i))_{i=1}^{n}$ has one pair per accepted requirement. Its age $a_i$ is the time from the start of tracking to first acceptance. Its weight $w_i$ represents the output score, calculated as the reference score multiplied by the fraction of the accepted requirement still satisfied $\Delta$ after acceptance. The labour list $B=((b_j,v_j))_{j=1}^{m}$ has one pair per contribution of human work to a task. Its age $b_j$ is the task's age at the end of the period represented by that contribution, and its weight $v_j$ expresses the labour contributed. Labour on unfinished, rejected and abandoned tasks belongs in this list. Assign shared work to tasks before calculating these contributions, so each person's time enters the sums once.

Choose one integer time unit for all task ages, such as hours. All ages and weights use unsigned 64-bit integers (\texttt{u64}). Output weights express the scores in millionths of a reference unit, and labour weights express person-hours in millionths. For example, a hypothetical output record with \texttt{age=72} and \texttt{weight=8000000} represents a requirement accepted 72 hours after tracking began whose later assessment gave an output score of eight reference units. A hypothetical labour record with \texttt{age=48} and \texttt{weight=500000} represents half a person-hour assigned to a period ending at task age 48 hours. The index sums the two kinds of weight separately.

For a nonnegative \texttt{u64} acceptance deadline $\tau$ and assessment delay $\Delta$, expressed in that time unit, the two totals are
\begin{equation}
\label{eq:discrete-cohort-totals}
 Q_{\mathrm{d}}(\tau)=\sum_{i=1}^{n} w_i\ind\{a_i\leq\tau\},
 \qquad
 H_{\mathrm{d}}(\tau,\Delta)=\sum_{j=1}^{m}v_j\ind\{b_j\leq\tau+\Delta\}.
\end{equation}
The result is the exact integer pair $(Q_{\mathrm{d}},H_{\mathrm{d}})$. Dividing its first value by its second gives reference output units per person-hour because both values use the same millionths scale. This ratio is defined only when $H_{\mathrm{d}}>0$. When labour is zero, the pair stores zero as its second value and the Rust method \texttt{ratio()} returns \texttt{None}. With positive labour, that method returns a floating-point approximation for display. The stored integer pair preserves the exact totals.

For the discrete labour total to equal the continuous integral in \eqref{eq:labour}, the selected contributions must sum to the labour accumulated by each queried cutoff. This equality holds when the contributions partition the cohort's labour into exact bin totals and no bin crosses a queried cutoff. Assigning a whole contribution to the end of a sampled interval or time bin instead approximates an interior cutoff.

Before supplying the age--weight pairs, check that the intended tasks are included once and that their acceptance times, labour totals and requirement assessments are available. Track changes to task scope through the original requirements and assessment notes. The index holds only the numeric fields needed for summation, so it cannot perform these checks. An output score also applies to the particular assessment delay $\Delta$ used to calculate it. Changing $\Delta$, the task set or the assessed scores requires new age--weight pairs and a rebuilt index. Section~\ref{sec:sharp-identification} explains how interval labour totals and each person's available time bound labour at a time inside a measured interval. The discrete index sums the supplied weights. Calculating attainable bounds for continuous labour allocations requires the separate optimisation described there.

Suppose each labour pair gives the exact person-hours $v_j$ for a time bin $[\ell_j,u_j)$ and its end age $b_j=u_j$, with each contribution counted once. The Rust labour sum then equals $H_-$ in \eqref{eq:binning-envelope} after unit conversion. That index stores no start keys and does not compute $H_+$. A companion index could sort interval starts and ends separately. It would sum intervals ending at or before the cutoff for the lower total, and intervals starting strictly before it for the upper total. This would require $O(m\log(m+1))$ preprocessing, $O(m)$ storage and $O(1+\log(m+1))$ time per cutoff. The two totals then bound labour when each time bin contributes its exact labour total once. The companion calculation's runtime remains to be measured.

\subsection{Construction, queries and correctness}

Algorithm~\ref{alg:build-horizon-index} prepares sorted ages and cumulative weights for the two fixed lists. A query includes all age--weight pairs at or before its cutoff. Pairs sharing an age are therefore included together, and their order has no effect on the total. Array positions start at one, with prefix entry zero storing the sum before the first pair. \Call{CheckedAdd128}{} converts a weight to 128 bits before addition and either returns the exact sum or reports \texttt{TotalOverflow}. An overflow stops construction before any index is returned. The Rust implementation sorts copies, leaving both input lists unchanged.

\begin{algorithm}[tb]
\caption[Build a cohort horizon index]{Build exact cumulative totals for a fixed cohort and follow-up}
\label{alg:build-horizon-index}
\begin{algorithmic}[1]
\Require{Accepted-output records $A$ and labour records $B$ as defined above, with ages and weights in the specified integer units.}
\Ensure{Sorted keys and exact prefix totals, or \texttt{TotalOverflow}.}
\ForAll{stream names $S$ in the ordered list $(A,B)$}
  \State $X_S\gets\Call{SortCopyByAge}{S}$
  \State $K_S\gets$ age array of $X_S$; $P_S[0]\gets0$
  \For{$j\gets1$ \textbf{to} $|X_S|$}
    \State $z\gets\Call{CheckedAdd128}{P_S[j-1],X_S[j].\mathrm{weight}}$
    \If{$z=\mathrm{overflow}$}
      \State \Return \texttt{TotalOverflow}
    \EndIf
    \State $P_S[j]\gets z$
  \EndFor
\EndFor
\State \Return $I=(K_A,P_A,K_B,P_B)$
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:query-horizon-index} uses the index to calculate totals for a list of acceptance deadlines without changing the index. \Call{UpperBound}{$K,x$} returns the number of sorted keys at most $x$, including every duplicate at the boundary. \Call{CheckedAdd64}{} reports \texttt{HorizonOverflow} if $\tau+\Delta$ cannot be represented. The entire batch is checked before any result is returned. Results follow the order of the supplied deadlines, which may arrive in any order.

\begin{algorithm}[tb]
\caption[Query a cohort horizon index]{Return exact output and labour totals for a batch of horizons}
\label{alg:query-horizon-index}
\begin{algorithmic}[1]
\Require{Index $I$, horizons $\tau_1,\ldots,\tau_q$ and the fixed follow-up $\Delta$.}
\Ensure{Exact total pairs in query order, or \texttt{HorizonOverflow}. No division is performed.}
\For{$r\gets1$ \textbf{to} $q$}
  \State $c_r\gets\Call{CheckedAdd64}{\tau_r,\Delta}$
  \If{$c_r=\mathrm{overflow}$}
    \State \Return \texttt{HorizonOverflow}
  \EndIf
\EndFor
\State $O\gets$ empty result array
\For{$r\gets1$ \textbf{to} $q$}
  \State $k_A\gets\Call{UpperBound}{K_A,\tau_r}$
  \State $k_B\gets\Call{UpperBound}{K_B,c_r}$
  \State Append $(P_A[k_A],P_B[k_B])$ to $O$
\EndFor
\State \Return $O$
\end{algorithmic}
\end{algorithm}
\endgroup

\begin{proposition}[Agreement with a full scan]
\label{prop:horizon-index}
If index construction and horizon addition succeed, each returned pair in \autoref{alg:query-horizon-index} equals \eqref{eq:discrete-cohort-totals}. This includes empty streams, repeated ages, zero weights and zero labour totals.
\end{proposition}
\begin{proof}
After construction has processed $j$ records of a sorted stream, its loop invariant is $P_S[j]=\sum_{\ell=1}^{j}X_S[\ell].\mathrm{weight}$. It holds at $j=0$ and checked addition preserves it. Sorting preserves the multiset of records. For a cutoff $x$, upper-bound binary search maintains a lower prefix whose keys are at most $x$ and an upper suffix whose keys exceed $x$. Its remaining interval strictly decreases until its bounds coincide at $k$. Thus exactly positions $1,\ldots,k$ meet the inclusive cutoff. The corresponding prefix total is the same sum a full scan selects. Apply this argument at $x=\tau$ for output and $x=\tau+\Delta$ for labour. The empty prefix has total zero, so the boundary cases follow without division.
\end{proof}

This proof establishes agreement for the discrete sums and operations above. It is outside the Lean proof coverage in Appendix~\ref{app:coverage}. The Rust tests compare indexing with a separately implemented full scan on the same ages and weights. Establishing whether those fields accurately represent acceptance times, output scores and person-hours requires measurement validation.

With $n$ output age--score pairs, $m$ labour age--weight pairs and $q$ queries, repeated scanning takes $O(q(1+n+m))$ time. Construction takes $O(n\log(n+1)+m\log(m+1))$ time and $O(n+m)$ additional storage. Indexed queries take $O(q(1+\log(n+1)+\log(m+1)))$ time and $O(q)$ result storage. These bounds count fixed-width operations and assume available memory. Preprocessing can outweigh the saving for a small batch, and an index cannot be reused after its input changes without maintaining or rebuilding its prefix totals.

\subsection{A reproducible performance comparison}

The benchmark uses a dependency-free Rust program to execute scanning and indexing on the same generated age--weight pairs and acceptance deadlines. It checks that both methods return identical integer totals, then compares their elapsed execution times. The timed indexed calculation includes building the index because the later queries must save enough time to recover that cost. The fixed assessment delay and generated numbers let this experiment compare the two methods within the Rust program. Applying the result to a company workload requires measurements on that workload. For further reading on data science with Rust, see Van Der Post~\cite{vanderpost2024datascience}. The runtime claims here rely on the executed benchmark and its saved timings.

The generated inputs contain 100,000 output age--score pairs and 400,000 labour age--weight pairs. The program generates these integers directly, without task identities, original requirements or measured human work. Task ages and acceptance deadlines use hours, with $\Delta=720$ and queried deadlines from 0 to 1,440. Three fixed random-number seeds (17, 41 and 93) determine the arrays and deadline sequences. For each seed and each $q\in\{1,10,100,1000\}$, five fresh processes execute one paired comparison. Each process first runs a full scan followed by an indexed calculation to warm up both methods. These warmups are excluded from the reported durations. The first timed method then alternates between scanning and indexing across paired comparisons. Both implementations return identical integer totals in every warmup and timed comparison. The benchmark was executed on 29 October 2026, and \texttt{results/raw.csv} contains all 60 measured pairs. Each row identifies the seed, repetition, query count and method order, alongside the elapsed times and an output checksum.

The executed build used Rust 1.85.1, optimisation level 3, one code-generation unit, no link-time optimisation and enabled overflow checks, on a shared Linux host reporting an Intel Xeon Platinum 8573C processor. Generating the arrays, process startup, warmup, checking the returned totals and writing results to disk were outside both timed regions. Indexed total time includes copying the input arrays, sorting, building cumulative totals, answering queries and freeing the index. The file \texttt{results/environment.json} identifies the compiler, source-file hashes and timing boundaries for this run. Host load was uncontrolled. Each query count has 15 measured pairs from repeated execution on three generated input arrays. These timings describe computation on those arrays rather than independently sampled production work.

Table~\ref{tab:horizon-performance} shows that indexing takes longer for a single query: median elapsed time increases from 2.889 to 21.016~ms. At ten queries, the median decreases by 26.0\%, but individual paired reductions range from $-16.4\%$ to $55.1\%$. Indexing therefore takes longer in 4 of the 15 comparisons at ten queries. At 100 and 1,000 queries, every measured pair favours the index. For 1,000 queries, the median falls from 2,787.159 to 23.051~ms, a 99.2\% reduction including construction and disposal.

The index pays the cost of sorting and building cumulative totals once, then answers each deadline query without summing the full input arrays again. The saved execution times support that approach for these generated arrays and query counts, subject to its storage and update costs. Arrays larger than available memory, changing ages or weights, other hardware and other query patterns require their own measurements. The benchmark program and its saved timing files let later comparisons reproduce the input generation, checks of exact totals and calculation of summary statistics.
