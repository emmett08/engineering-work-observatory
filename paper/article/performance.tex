\section{Computing repeated cohort summaries}
\label{sec:performance}

How can we calculate productivity for many acceptance deadlines without rescanning every record? Sort the records once and store cumulative totals, so each later query needs only two binary searches. For a fixed set of tasks and assessment delay $\Delta$, one sum counts the output scores for tasks accepted by the deadline and the other counts labour through task age $\tau+\Delta$. A full scan calculates the same two totals directly. The comparison below measures the time needed to calculate those totals. Establishing an effect of AI assistance on human labour requires a separate causal study.

\subsection{Discrete input records and units}

The index receives two lists of records. Let $A=((a_i,w_i))_{i=1}^{n}$ contain one output record per accepted requirement. Its acceptance age $a_i$ is the time from the start of tracking to first acceptance. Its output score $w_i$ is the reference score multiplied by the fraction of the accepted requirement still satisfied $\Delta$ after acceptance. Let $B=((b_j,v_j))_{j=1}^{m}$ contain labour contributions assigned to tasks, including unfinished, rejected and abandoned tasks. Each $b_j$ is the associated task's age at the end of the period represented by that labour contribution. Shared work is assigned to tasks before these records are formed.

Choose one integer time unit for all task ages, such as hours. All ages and weights are nonnegative \texttt{u64} integers. Output weights express the output scores in millionths of a reference unit. Labour weights express the labour contributions in millionths of a person-hour. The index sums output weights and labour weights separately.

For a nonnegative \texttt{u64} acceptance deadline $\tau$ and assessment delay $\Delta$, expressed in that time unit, the two totals are
\begin{equation}
\label{eq:discrete-cohort-totals}
 Q_{\mathrm{d}}(\tau)=\sum_{i=1}^{n} w_i\ind\{a_i\leq\tau\},
 \qquad
 H_{\mathrm{d}}(\tau,\Delta)=\sum_{j=1}^{m}v_j\ind\{b_j\leq\tau+\Delta\}.
\end{equation}
The result is the exact integer pair $(Q_{\mathrm{d}},H_{\mathrm{d}})$. Dividing its first value by its second gives reference output units per person-hour because both values use the same millionths scale. This ratio is defined only when $H_{\mathrm{d}}>0$. When labour is zero, the pair stores zero as its second value and the Rust method \texttt{ratio()} returns \texttt{None}. With positive labour, that method returns a floating-point approximation for display. The stored integer pair preserves the exact totals.

For the discrete labour total to equal the continuous integral in \eqref{eq:labour}, the selected contributions must sum to the labour accumulated by each queried cutoff. This equality holds when the contributions partition the cohort's labour into exact bin totals and no bin crosses a queried cutoff. Assigning a whole contribution to the end of a sampled interval or time bin instead approximates an interior cutoff.

The measurement protocol must also address missing labour measurements and requirement assessments. It must track duplicate task records and changes to task scope. The index sums the records supplied to it, so these checks belong to data collection. Output scores apply to the particular assessment delay $\Delta$ used to calculate them. Changing $\Delta$, the task set or its output scores requires corresponding input data and a rebuilt index. Section~\ref{sec:sharp-identification} explains how exact interval labour totals and capacity restrictions bound labour at a time inside an observed interval. The discrete index below computes the supplied record totals. Calculating attainable bounds for continuous labour allocations requires the separate optimisation described there.

If the labour records contain exact, nonduplicated labour totals $v_j$ for bins on $[\ell_j,u_j)$ with end ages $b_j=u_j$, the Rust labour sum equals $H_-$ in \eqref{eq:binning-envelope} after unit conversion. That index stores no start keys and does not compute $H_+$. A companion index could sort interval starts and ends separately. It would sum intervals ending at or before the cutoff for the lower total, and intervals starting strictly before it for the upper total. This would require $O(m\log(m+1))$ preprocessing, $O(m)$ storage and $O(1+\log(m+1))$ time per cutoff. The two totals then give lower and upper labour bounds when bins have exact, nonduplicated labour totals. The companion calculation's runtime remains to be measured.

\subsection{Construction, queries and correctness}

Algorithm~\ref{alg:build-horizon-index} prepares an index of sorted ages and cumulative weights for the two fixed record lists. Records with equal ages are included or excluded together, so their order within that age has no effect on a query. Record positions start at one, and prefix entry zero stores the sum before the first record. \Call{CheckedAdd128}{} converts a weight to 128 bits before addition and either returns the exact sum or reports \texttt{TotalOverflow}. An overflow stops construction before any index is returned. The Rust implementation sorts copies of the input lists, preserving the caller's records.

\begin{algorithm}[tb]
\caption[Build a cohort horizon index]{Build exact cumulative totals for a fixed cohort and follow-up}
\label{alg:build-horizon-index}
\begin{algorithmic}[1]
\Require{Accepted-output records $A$ and labour records $B$ as defined above, with ages and weights in the specified integer units.}
\Ensure{Sorted keys and exact prefix totals, or \texttt{TotalOverflow}.}
\ForAll{stream names $S$ in the ordered list $(A,B)$}
  \State $X_S\gets\Call{SortCopyByAge}{S}$
  \State $K_S\gets$ age array of $X_S$; $P_S[0]\gets0$
  \For{$j\gets1$ \textbf{to} $|X_S|$}
    \State $z\gets\Call{CheckedAdd128}{P_S[j-1],X_S[j].\mathrm{weight}}$
    \If{$z=\mathrm{overflow}$}
      \State \Return \texttt{TotalOverflow}
    \EndIf
    \State $P_S[j]\gets z$
  \EndFor
\EndFor
\State \Return $I=(K_A,P_A,K_B,P_B)$
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:query-horizon-index} uses the index to calculate totals for a list of acceptance deadlines without changing the index. \Call{UpperBound}{$K,x$} returns the number of sorted keys at most $x$, including every duplicate at the boundary. \Call{CheckedAdd64}{} reports \texttt{HorizonOverflow} if $\tau+\Delta$ cannot be represented. The entire batch is checked before any result is returned. Results follow the order of the supplied deadlines, which may arrive in any order.

\begin{algorithm}[tb]
\caption[Query a cohort horizon index]{Return exact output and labour totals for a batch of horizons}
\label{alg:query-horizon-index}
\begin{algorithmic}[1]
\Require{Index $I$, horizons $\tau_1,\ldots,\tau_q$ and the fixed follow-up $\Delta$.}
\Ensure{Exact total pairs in query order, or \texttt{HorizonOverflow}. No division is performed.}
\For{$r\gets1$ \textbf{to} $q$}
  \State $c_r\gets\Call{CheckedAdd64}{\tau_r,\Delta}$
  \If{$c_r=\mathrm{overflow}$}
    \State \Return \texttt{HorizonOverflow}
  \EndIf
\EndFor
\State $O\gets$ empty result array
\For{$r\gets1$ \textbf{to} $q$}
  \State $k_A\gets\Call{UpperBound}{K_A,\tau_r}$
  \State $k_B\gets\Call{UpperBound}{K_B,c_r}$
  \State Append $(P_A[k_A],P_B[k_B])$ to $O$
\EndFor
\State \Return $O$
\end{algorithmic}
\end{algorithm}
\endgroup

\begin{proposition}[Agreement with a full scan]
\label{prop:horizon-index}
If index construction and horizon addition succeed, each returned pair in \autoref{alg:query-horizon-index} equals \eqref{eq:discrete-cohort-totals}. This includes empty streams, repeated ages, zero weights and zero labour totals.
\end{proposition}
\begin{proof}
After construction has processed $j$ records of a sorted stream, its loop invariant is $P_S[j]=\sum_{\ell=1}^{j}X_S[\ell].\mathrm{weight}$. It holds at $j=0$ and checked addition preserves it. Sorting preserves the multiset of records. For a cutoff $x$, upper-bound binary search maintains a lower prefix whose keys are at most $x$ and an upper suffix whose keys exceed $x$. Its remaining interval strictly decreases until its bounds coincide at $k$. Thus exactly positions $1,\ldots,k$ meet the inclusive cutoff. The corresponding prefix total is the same sum a full scan selects. Apply this argument at $x=\tau$ for output and $x=\tau+\Delta$ for labour. The empty prefix has total zero, so the boundary cases follow without division.
\end{proof}

This analytical proof establishes agreement for these discrete sums and operations. It is outside the Lean proof coverage in Appendix~\ref{app:coverage}. The Rust tests compare the indexed implementation with a separately implemented full scan. Successful tests do not establish completeness or reliability of the underlying observations.

With $n$ acceptance records, $m$ labour records and $q$ queries, repeated scanning takes $O(q(1+n+m))$ time. Construction takes $O(n\log(n+1)+m\log(m+1))$ time and $O(n+m)$ additional storage. Indexed queries take $O(q(1+\log(n+1)+\log(m+1)))$ time and $O(q)$ result storage. These bounds count fixed-width operations and assume available memory. Preprocessing can outweigh the saving for a small batch, and an index cannot be reused after its input changes without maintaining or rebuilding its prefix totals.

\subsection{A reproducible performance comparison}

The supplement's dependency-free Rust program compares scanning and indexing on the same generated records and lists of acceptance deadlines. It retains the exact totals for equality checks and times computation separately from data generation. The benchmark includes construction time because a batch must save at least that time in queries to recover the cost of building the index. The fixed assessment delay and generated inputs let the comparison measure the choice between scanning and indexing within the Rust program. Applying the result to a company workload requires a comparison on that workload. For further reading on data science with Rust, see Van Der Post~\cite{vanderpost2024datascience}. The runtime claims here rely on the accompanying measurements.

The workload contains 100,000 generated output records and 400,000 generated labour contributions. These arrays supply the values needed for the sums, without a task list or links assigning individual contributions to tasks. Task ages and acceptance deadlines use hours, with $\Delta=720$ and queried deadlines from 0 to 1,440. Three fixed random-number seeds (17, 41 and 93) define the datasets and deadline sequences. For each seed and each $q\in\{1,10,100,1000\}$, five fresh processes each run one paired comparison. Each process first performs an unmeasured full scan followed by an unmeasured indexed run. Measured method order then alternates across observations. These timings therefore describe repeated computation after both methods have run once. Both implementations return identical integer pairs in every warmup and measured comparison. All 60 measured pairs are retained.

The build uses Rust 1.85.1, optimisation level 3, one code-generation unit, no link-time optimisation and enabled overflow checks, on a shared Linux host reporting an Intel Xeon Platinum 8573C processor. Dataset generation, startup, warmup, output verification and result I/O are outside both timed regions. Indexed total time includes input copies, sorting, prefix construction, queries and disposal of the index. The environment record retains the compiler details, source hashes and timing boundaries. Host load is uncontrolled. The 15 pairs per query count are repeated measurements of three synthetic datasets, not independent samples of production work.

The index pays the cost of sorting and building cumulative totals once, then avoids rescanning every record for each deadline. The observed saving supports that approach for this fixed workload and query pattern, subject to its storage and update costs. Datasets larger than available memory, changing records, other hardware and other query patterns require their own measurements. The raw paired timings and supporting programs allow those comparisons to repeat the generation, exact-output checks and summaries.
