\begin{abstract}

How can we forecast how many pull requests a monitored team will merge during the next complete calendar period? The default model assigns probabilities according to how often each merge count occurred in earlier completed periods that meet the collection requirements. The target count includes requests opened after the forecast is produced. To obtain the historical counts, the collector retrieves all pages of the visible pull-request inventory and saves repository and request identifiers, merge timestamps and collection details. The predictive assumption is that these historical frequencies approximate probabilities for the next count, without requiring stationary queues or independent days. The proportion of future counts falling within the forecast's percentile ranges must be measured in subsequent evaluation. The report also describes currently open requests. Predicting which resources will constrain future work requires additional evidence.

In a predeclared comparison over 26 weeks in a public repository, a model fitted to recent history has a worse score for its predicted probabilities than a comparator using expanding history and fails the criterion for replacing the default. We therefore retain the default history-selection rule. The comparison uses a bounded training history and leaves the default's full-history forecasts unvalidated. The user repositories also have too little calendar history to establish predictive accuracy. Their daily forecast is experimental, and weekly and fortnightly forecasts await the required observations. The contribution is a reproducible procedure for collecting merge counts, issuing forecasts and evaluating them, together with the comparison that supported retaining the default.
\end{abstract}

\section{Forecasting the next period's merge count}

A team with an empty pull-request queue can still merge requests tomorrow if those requests are opened during the day. A large queue can yield few merges when requests wait, are abandoned or fall outside the team's immediate priorities. Forecasting total merge activity therefore requires a target that includes future arrivals as well as the resolution of today's backlog.

We ask how many distinct pull requests (PRs), visible through GitHub in a fixed set of repositories, will have a merge timestamp in a specified future interval. The selected repositories define the monitored portfolio. Contributors can work across teams, and a team's work can extend beyond those repositories. Establishing how well the portfolio represents a team's activity therefore requires separate evidence. Counts also depend on how work is divided into PRs, on automation and on the repository's rules for accepting and merging requests. We use the term \emph{merge count} to keep that measured quantity explicit.

The automatic workflow counts merges in each completed calendar period from the visible PR inventory and uses these counts to forecast probabilities for a future period. A later collection supplies the outcome for scoring once that period has elapsed. We recommend this as the initial forecasting procedure. The companion manuscript's bounds on possible labour totals and its sampling results address labour measurement with additional observations. They supply neither inputs to this forecast nor evidence of its accuracy.

\section{Collection requirements and calendar boundaries}
\label{sec:data}

Each merge must be counted once within a fixed repository scope. Let $\mathcal R$ be a fixed set of stable repository identifiers. Deduplicate records by repository identity and PR identity. Retain each raw response with its content digest, collection time and pagination coverage so that the count can be reconstructed and its source coverage inspected. GitHub's PR endpoint exposes the creation and merge timestamps needed for the count \citep{githubpulls}. The PR inventory supplies these inputs without code diffs, workflow logs or personal activity labels.

Within that scope, merge timestamps determine each period's count. For a future half-open interval $I=[a,b)$, define
\begin{equation}
 Y_I=\sum_{r\in\mathcal R}\sum_{i\in\mathcal P_r}
       \ind\{a\leq m_i<b\},
 \label{eq:count}
\end{equation}
where $\mathcal P_r$ denotes the PR identifiers in the saved records for repository $r$ and $m_i$ is the merge timestamp, when one exists. An unmerged closure contributes zero. A close--reopen--merge history contributes one at its eventual merge. Requests created after $a$ are included when they merge before $b$. A timestamp equal to $b$ belongs to the next interval.

The visible inventory determines the population being counted. Successful pagination establishes what GitHub returned under the collector's access permissions. Deleted, transferred or inaccessible historical records may remain absent, and an incomplete response leaves the count unavailable.

The calendar history must also distinguish complete zero-count periods from periods outside observation. Each training interval must lie within the declared observation frame and after every selected repository's creation. Discard the initial partial period and the current incomplete period. A day before a repository existed falls outside the population and cannot supply a zero-activity observation.

Collection timing determines which completed periods can enter the history. Each saved collection manifest links its throughput summary to the returned PR records. The summary records collection start and end times, required sources and their coverage. We treat historical counts as complete only through a conservative time limit, called the \emph{complete-through cutoff}. For the selected repositories, this is the earliest start time among their latest usable collections. An eligible training interval ends at or before that cutoff and meets the observation-frame requirements above. This rule prevents a stale inventory, or a collection whose pages are retrieved across midnight, from adding spurious zero days. Record the cutoff separately from snapshot creation and forecast issuance. The inventory was scanned over the recorded collection span, so its contents may describe changes during that span.

\paragraph{Collection, training and target times.}
The cutoff limits the training history. The time when the forecast is produced, called its issue time, sets the earliest permitted start of the future target period. A forecast issued during a UTC day targets the next complete UTC day. Weekly periods start on Monday at 00:00 UTC. Training intervals end at or before the cutoff, and a future target period starts no earlier than the issue time. Save collection and issue times alongside the cutoff and target boundaries to show the gap between training and the future target.

\paragraph{Reconstructed forecasts and forecasts saved before the target starts.}
\emph{Retrospective reconstruction} uses timestamps in the current visible inventory to form earlier counts. It assumes that those timestamps faithfully describe earlier events, while leaving the observer's knowledge at those earlier times unestablished. Running today's software with an old cutoff still produces a retrospective reconstruction. Mutable current fields such as draft status, head commit, review state and change size must be excluded from predictors of historical counts.

\emph{Prospective evaluation} instead uses collection records and forecasts saved by the automatic workflow before the target period starts. Save the repository scope and the hash of the source records or snapshot to identify the observations used. Record the model version and fitted intervals with the target interval and issued probability distribution to identify the calculation and the outcome it predicts. Together, these records allow the calculation and declared sequence of times to be checked. Independent verification of the declared times remains absent.

\section{The default empirical model and recent-window challenger}
\label{sec:model}

The forecast assigns probability according to how often each count occurred in the eligible history. Suppose $x_1,\ldots,x_n$ are the total merge counts for the selected repositories in preceding complete calendar periods. The default model uses all eligible complete periods within the specified repositories and observation dates. Its probability mass function and cumulative distribution function are
\begin{equation}
 \widehat p(k)=\frac1n\sum_{j=1}^n\ind\{x_j=k\},
 \qquad
 \widehat F(k)=\frac1n\sum_{j=1}^n\ind\{x_j\leq k\}.
 \label{eq:ecdf}
\end{equation}
Repeated counts retain their frequency, including genuine zero periods. Each portfolio observation totals repository counts from the same interval. Sum these synchronised counts before applying \eqref{eq:ecdf}. Convolving separately fitted repository distributions would impose a dependence structure absent from the observations and is excluded from this procedure.

Each target uses the calendar boundaries and minimum history below, fixed before evaluating model scores. Their predictive adequacy requires evaluation.

The challenger limits that history to at most eight daily or weekly observations, or four fortnightly observations, with the same four-observation minimum. The daily target was added for repositories too young to supply the history required by the predeclared weekly benchmark. That benchmark remains unchanged.

The weekly target still requires weekly observations. Multiplying a daily forecast by seven or convolving seven copies of its distribution does not meet the specification. Fourteen-day evaluation uses every other Monday, with parity anchored to 5 January 1970, so adjacent scored target intervals do not overlap. Each forecast records the method and model version.

Report the empirical mean as the expected merge count and a predictive median as the point forecast evaluated by absolute error. The inverse-CDF 10th and 90th percentiles describe the distribution's spread. Report their inclusive probability mass and training size, because discreteness can make that mass differ from the percentile labels. For eight distinct observations, the endpoints are the sample minimum and maximum and enclose all fitted mass. Describing that range as an exactly 80\% probability interval would misstate its discrete mass. Its future coverage must be measured separately.

Future activity can exceed the historical maximum. Equation~\eqref{eq:ecdf} nevertheless assigns zero mass to unobserved counts, including an unprecedented burst. Four zero days likewise yield a point mass at zero even though future activity can vary. The report must therefore show the observed counts and their frequencies so that the reader can inspect this limitation.

\subsection{The assumption connecting past counts to future activity}

Computing \eqref{eq:ecdf} uses observed frequencies. It requires no Poisson arrival process, independence of PR completions or calendar periods, proportional hazards or stationary queue equilibrium. The predictive step adds the approximation $\Prb(Y_{\mathrm{next}}\leq k\mid\mathcal H)\approx\widehat F(k)$, where $\mathcal H$ is the recorded history. Future scores test whether the selected historical outcomes inform the next interval closely enough for this approximation to be useful.

A launch burst, changed working pattern, repository migration or change in PR size can break that predictive relationship. Keeping all eligible history can retain obsolete activity, while a recent window can discard informative history. Comparative scores therefore guide the choice between them. Neither rule has a universal advantage. Four to eight days provide little evidence about day-of-week effects and almost none about longer cycles.

An observed past, without assumptions about its continuation, supplies no informative upper bound on future merges. Two continuations can share every recorded event through the cutoff and then produce zero or many merges. The empirical forecast combines event accounting with a testable assumption that historical counts inform the next interval. A more elaborate model should justify its additional inputs and assumptions through better predictions of subsequent outcomes on the same target.

\section{What counts and ages show about open pull requests}
\label{sec:queue}

The same inventory also describes pull requests still open. A fresh collection reports the number observed, their ages since creation and the oldest recorded requests. It also permits separate counts of open drafts, requests with a nonempty requested-reviewer or requested-team list, and requests at least seven days old. The seven-day threshold is a fixed descriptive choice. One request can belong to several sets, so summing their counts can double-count requests. An absent optional field leaves the corresponding count unavailable, while a known empty inventory has zero items in each set.

Compute creation age at the source observation time and report the collection span and its age at forecast issuance. Creation age measures elapsed time since opening. It cannot distinguish time waiting for review from active processing or other delays. The throughput collector omits submitted-review status and continuous-integration (CI) outcomes. These current-inventory observations are excluded from predictors used in retrospective count forecasts.

Inventory changes depend on the events adding and removing requests. For a complete history of state transitions, let $B$ be open inventory, $A$ new openings, $R$ reopenings, $M$ merges and $C$ closures without merge. On an interval $I$,
\begin{equation}
 B_{\mathrm{end}}=B_{\mathrm{start}}+A_I+R_I-M_I-C_I.
 \label{eq:conservation}
\end{equation}
Count a merge-induced closure once, in $M_I$, and exclude it from $C_I$. Final \texttt{closed\_at} values leave repeated close and reopen episodes unobserved. GitHub exposes timeline events from which such transitions can be studied, but the throughput collector does not collect the history required to reconstruct them \citep{githubevents}.

When the state transitions are observed, Equation~\eqref{eq:conservation} checks whether the inventory change agrees with the event counts. Forecasting requires separate estimates of its future terms. Little's finite-window analysis likewise treats initial inventory and the time accumulated within the observation window explicitly when relating sample-path measurements \citep[Sections 2.1--2.3]{little2011}. Dividing today's backlog by mean latency among completed PRs supplies neither a forecast of next week's throughput nor an estimate of the effect of adding a reviewer.

The recent \emph{Queue \& AI} model illustrates how variation in service times and rework can affect queueing delays. To relate activity to those delays, it requires human-attention service requirements, effective reviewer capacity and quantities describing errors and rework. Its main calculation assumes a stable single-server queue with Poisson arrivals, while an alternative uses a queue approximation \citep[Sections 2.1, 3 and 4.2]{bartolucci2026}. PR timestamps leave those inputs unmeasured. Applying this mechanism to the monitored repositories would therefore require a separate study to estimate them and assess the queue assumptions.

Workflow outcomes offer possible additional predictors or forecast targets, with their own interpretation limits. An initial CI failure records the outcome of a workflow run without measuring product correctness. The retained history must preserve that initial outcome when a later rerun succeeds. The existing collector can retain run attempts separately, and GitHub's API distinguishes them \citep{githubattempts}. Missing, cancelled and skipped runs require separate treatment. Reopening a PR likewise records a transition while leaving its reason unspecified. Such observations may support further predictive evaluation, but they do not identify the cause of a throughput change or the effect of a staffing intervention.

The implementation consequently reports current queue counts. Forecasting a specified queue count at a future time would require regularly saving the open-request inventory, then scoring the forecast when an inventory for the target time had been collected. Establishing which resource constrains the work and how staffing changes would alter that constraint requires additional evidence even if those count forecasts become accurate. Forecasts of future queue counts and resource constraints therefore require further work.

\section{A test that can reject the model}
\label{sec:evaluation}

Evaluation must preserve the information available when each forecast was fitted. At each time chosen for a historical forecast, train only on completed earlier intervals and evaluate on a target period that has ended, using source records meeting the collection requirements below. Future merges enter the outcome only. Report forecasts with insufficient history, incomplete collection or target periods that have not yet ended as unavailable results. Scoring known positive outcomes while omitting unresolved targets would select the evaluation sample using outcome information. Retrospective reconstructions are reported separately from forecasts saved before their target periods began.

The archive scorer checks the calculation and declared sequence of times in bundles saved by the forecast command. Each bundle contains the source snapshot, prepared history, method and forecast. The scorer checks creation time against the source cutoff and target start, verifies the source digest, reconstructs the history and recomputes the distribution. These checks establish whether the inputs reproduce the forecast and the declared times occur in the required order. The limitation on independently verified times remains as described in Section~\ref{sec:data}, and offline reconstructions remain identifiable as reconstructions.

Before scoring, the scorer requires a later collection covering the same numeric repository identifiers, with a conservative complete-through cutoff at or beyond the target end. A target awaiting that cutoff remains pending. Incomplete inputs and malformed archives remain visible as unavailable results or errors. Scoring preserves the original archive.

Once the target is observed, scoring compares the distribution with the realised count. The primary loss is the discrete ranked probability score (RPS), equivalent to the continuous ranked probability score (CRPS) restricted to nonnegative integers,
\begin{equation}
 L(F,y)=\sum_{k=0}^{\infty}\bigl(F(k)-\ind\{y\leq k\}\bigr)^2.
 \label{eq:rps}
\end{equation}
For a finite empirical distribution, an independent computational check is
\begin{equation}
 L(\widehat F,y)=\frac1n\sum_{i=1}^n|x_i-y|
 -\frac{1}{2n^2}\sum_{i=1}^n\sum_{j=1}^n|x_i-x_j|.
 \label{eq:pairwise}
\end{equation}
Equation~\eqref{eq:pairwise} uses the nonnegative loss orientation of the standard CRPS identity \citep[Section 4.2]{gneiting2007}. The independent draws from $F$ in that identity are draws from the issued probability distribution. The identity imposes no independence assumption on the historical counts used to construct it. A point-mass forecast reduces to absolute error, allowing direct comparison with deterministic baselines. A previously unseen large count receives a finite penalty.

RPS evaluates the complete distribution. Report mean RPS and paired losses against each fixed comparator to show comparative distributional performance. Calibration asks whether predicted probabilities agree with outcomes, which a narrow predicted range alone cannot establish \citep{gneitingcalibration2007}.

The point and interval summaries answer more specific questions. Mean absolute error (MAE) evaluates the predictive median. The width of the empirical percentile range describes its spread, and achieved coverage is the proportion of observed target counts falling within that range. Report the predictive mean separately. Each summary also needs the training size, number of forecast dates evaluated and counts of unavailable target periods or those that have not yet ended, so that the reader can identify the observations behind it.

The predeclared weekly comparators are an expanding-history empirical distribution, a point mass at zero, a point mass at the previous week's count, and a Poisson distribution whose mean is the preceding four weekly counts' mean. The Poisson distribution serves as a restrictive forecast benchmark. Its inclusion leaves the observed process's distribution unspecified. Apply the corresponding predeclared comparators to the experimental daily target. The recent and expanding empirical models coincide until observations fall outside the recent window. Keep the predeclared window and comparator set fixed throughout evaluation.

For the public-repository comparison, \texttt{cpmpy/cpmpy} and a 78-week window were chosen before inspecting model scores. The first 52 complete UTC weeks initialise the history. The following 26 weeks provide chronological targets, and each subsequent forecast may use earlier observed evaluation weeks. The expanding comparator therefore uses 52--77 weeks of training history. The comparison evaluates these fixed methods in one repository population. Its results leave accuracy in the user's repositories unestablished.

The period covered by the training data limits the comparison with the default, which uses all eligible history for the selected repositories. The public comparison's expanding model uses only the specified 52--77 weeks of training history. Failure of the recent-window challenger to replace that comparator therefore leaves the default model's predictive accuracy and general comparative performance unestablished.

The provisional criterion for replacing the default requires at least 5\% lower mean RPS than the expanding empirical comparator. This threshold was chosen for the evaluation. If the comparator has zero loss, percentage improvement is unavailable. The protocol also calls for limiting any increase in MAE, but the maximum permitted increase remains unspecified.

A confident superiority claim additionally needs an uncertainty analysis. Enough calendar observations must be available for a predeclared analysis that accounts for dependence and yields a positive lower bound on improvement. The required number of periods remains to be specified. Nonoverlapping periods can still be serially dependent, and observations from two repositories need not be independent replications. Resampling a few days preserves the limitations of that short observation period.

\paragraph{Implementation checks.}
The implementation checks test count construction and the information available at forecast issuance. Exact boundary timestamps must enter the correct half-open interval, and requests created and merged within the target must count. Complete periods with zero merges must remain in the history, while incomplete source pages must leave counts unavailable. Duplicate source versions must leave counts unchanged. Changing or appending events after a cutoff must leave the corresponding forecast unchanged. Current mutable fields must leave historical count forecasts unchanged. Independent evaluation of \eqref{eq:rps} and \eqref{eq:pairwise} checks numerical correctness. Predictive accuracy requires the subsequent-outcome comparisons described above.

\section{Retained forecasts and comparison results}

The user results demonstrate the procedure on several days of repository history. That history permits automatic inventory extraction and an experimental daily forecast once four complete days are available. With five complete daily observations, the default model and recent-window challenger produce the same distribution. Weekly and fortnightly forecasts remain unavailable until their required numbers of complete periods have accumulated. This short history leaves weekly accuracy, seasonality and comparative predictive performance unvalidated.

\subsection{Evaluating subsequent user forecasts}

The public-repository comparison supplies a test of the candidate methods on its declared weekly history. The user example demonstrates collection and forecast issuance on a shorter daily history. Assessing that forecast's accuracy requires retaining it unchanged and scoring the outcome after its target has elapsed.

The procedure can now accumulate checkable forecasts and subsequent scores. It specifies which repository events enter each count, when a forecast can be produced and when outcomes can be scored, without asking contributors to classify their work. The recent-window model's failure to improve on the expanding-history comparator supports retaining the default history-selection rule while forecasts accumulate. Identifying capacity bottlenecks requires additional observations or justified assumptions. Measuring labour productivity or correctness, and estimating causal effects of AI or staffing, likewise requires evidence beyond merge counts.
